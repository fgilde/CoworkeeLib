# DTOs und Mapping

DTOs lassen sich von Hand schreiben, und viele sind es auch: Requests, Dashboards und andere Formen, die keine Entity abbilden. Für DTOs, die eine Entity abbilden, erzeugt das optionale Paket `Coworkee.CodeGen` sie aus der Entity, zusammen mit dem Mapping in beide Richtungen. Es bringt den Source-Generator [Nextended.CodeGen](https://fgilde.github.io/Nextended/projects/codegen) mit; gemappt wird entweder mit einfachen Extension-Methoden oder mit einem [Mapperly](https://mapperly.riok.app/)-Mapper, pro Entity wählbar.

## Einschalten

Das Paket gehört in das Projekt mit den Entities, meist das Modulprojekt:

```xml title="MyApp.Catalog/MyApp.Catalog.csproj"
<PackageReference Include="Coworkee.CodeGen" />
<!-- nur für Entities, die mit Mapperly mappen -->
<PackageReference Include="Riok.Mapperly" PrivateAssets="all" ExcludeAssets="runtime" />
```

Daneben liegt eine `codegen.json`. Das Paket findet sie über den Namen; ohne sie wird nichts erzeugt.

```json title="MyApp.Catalog/codegen.json"
{
  "DtoGeneration": {
    "Namespace": "MyApp.Catalog",
    "OutputPath": "../MyApp.Contracts/Catalog/Generated/",
    "MappingOutputPath": "./Generated/",
    "DeepProperties": true,
    "PropertiesToIgnore": [ "TenantId", "CreatedAt", "CreatedBy", "ModifiedAt", "ModifiedBy", "IsDeleted", "DeletedAt", "DeletedBy" ],
    "CreateFileHeaders": false,
    "CreateRegions": false,
    "DefaultMappingSettings": { "ToSourceMethodName": "ToEntity" }
  }
}
```

| Einstellung | Wozu |
|---|---|
| `OutputPath` | Die DTOs landen im Contracts-Projekt, so teilen API, Blazor-Client und SDKs sie. Das Contracts-Projekt braucht dafür nichts. |
| `MappingOutputPath` | Die Mappings bleiben im Modulprojekt, dem einzigen, das Entities und DTOs kennt. |
| `Namespace` | Namespace der Mappings. Mit dem Root-Namespace des Moduls steht `brand.ToDto()` in jedem Handler ohne `using` bereit. |
| `DeepProperties` | Übernimmt die `Id` aus `Entity` ins DTO. |
| `PropertiesToIgnore` | Spalten, die kein DTO tragen soll. Ein Attribut kann eine eigene Liste setzen. |
| `CreateFileHeaders: false` | Hält den Zeitstempel aus den Dateien heraus; ein Build ändert sie nur, wenn sich die Entity geändert hat. |
| `DefaultMappingSettings` | Methodennamen; `ToDtoMethodName` ist standardmäßig `ToDto`. |

Die erzeugten Dateien sind normale Quelldateien im Repository und werden im Pull Request geprüft wie jede andere Änderung. Neu geschrieben werden sie nur, wenn der Build eine geänderte Entity sieht; eine Änderung ist nach dem nächsten Build sichtbar. Wer eine Datei löscht, bekommt sie beim nächsten Build neu.

Geschrieben werden die Dateien, während das Modul kompiliert, also nach dem Build des Contracts-Projekts: Code, der ein neues DTO verwendet, kompiliert ab dem nächsten Build. Um ein handgeschriebenes DTO zu ersetzen, die Entity markieren und einmal bauen, solange das handgeschriebene DTO noch existiert, dann es und sein Mapping löschen.

## Entities markieren

```csharp title="MyApp.Catalog/Domain/Brand.cs"
[AutoGenerateDto(Namespace = "MyApp.Contracts.Catalog")]
public sealed class Brand : AuditedEntity, IMultiTenant
{
    public required string Name { get; set; }
    public string? Description { get; set; }
    public decimal Tax { get; set; }
    public Guid TenantId { get; set; }
}
```

```csharp title="MyApp.Contracts/Catalog/Generated/BrandDto.g.cs (erzeugt)"
public partial class BrandDto : IBrandDto
{
    public required string Name { get; set; }
    public string? Description { get; set; }
    public decimal Tax { get; set; }
    public System.Guid Id { get; set; }
}
```

`required`-Member bleiben `required`, nullbare bleiben nullbar, und die Klasse ist `partial`, das Contracts-Projekt kann sie also ergänzen. `[IgnoreOnGeneration]` an einer Property oder `PropertiesToIgnore` am Attribut lässt Member weg, `[GenerationPropertySetting(PropertyName = ...)]` benennt sie um. Alle Optionen stehen in der [Nextended.CodeGen-Referenz](https://fgilde.github.io/Nextended/projects/codegen).

`Coworkee.CodeGen` bringt Nextended.CodeGen 10.1.61 mit. Ein zweites `[AutoGenerateDto]` an einer Entity erzeugt ein weiteres DTO von ihr mit eigenem Mapping, eine *View* (eine andere Form für einen anderen Client, eine Listenzeile, einen Export): siehe [DTO-Views](https://fgilde.github.io/Nextended/de/projects/codegen#dto-views-mehrere-dtos-einer-entity). Eine Entity mit einem Attribut erzeugt dasselbe wie bisher.

## Im Code konfigurieren (Fluent)

Statt Attributen an den Entities (oder zusätzlich) konfiguriert eine Klasse im Modul, die von `CodeGenConfig` erbt, die Generierung: welche Entities ein DTO bekommen, ausgelassene oder umbenannte Member, Views, Reihenfolge der Member und Facetten. Das ist der Weg, wenn die Entities frei von Generierungs-Attributen bleiben müssen, etwa bei einem Modell, das aus einem anderen Repository kopiert wird. Attribute und `codegen.json` funktionieren weiter; die Fluent-Regeln verfeinern sie (json, dann Attribute, dann Fluent).

```csharp title="MyApp.Catalog/CodeGen/CatalogCodeGen.cs"
using Nextended.Core.CodeGen;
using Nextended.Core.Facets;

public sealed class CatalogCodeGen : CodeGenConfig
{
    public CatalogCodeGen()
    {
        Defaults(d => d.Namespace("MyApp.Contracts.Catalog").OutputPath("../MyApp.Contracts/Catalog/Generated"));

        Dto<Brand>(d => d
            .Ignore(x => x.Tax)
            .Property(x => x.Description, p => p.Name("Notes"))
            .Property(x => x.Country, p => p.Attribute<CountryCodeAttribute>())   // typisiert: [global::Coworkee.Contracts.Data.CountryCode]
            .View("BrandRow", v => v.Ignore(x => x.Description)));             // ein zweites DTO: BrandRow

        ViewDefaults(v => v.Ignore("DateCreatedUtc", "DateUpdatedUtc"));     // für jede View

        Facets<Product>(f => f                                                 // Facetten ohne [ProvideFacet]
            .Facet(x => x.BrandId, o => o.Label("Marke").ValuePath("BrandId").LabelPath("Brand.Name").ValueType<Guid>())
            .Facet(x => x.ReleasedAt, o => o.Label("Erschienen").Type(FacetType.DateRange)));
    }
}
```

Die Klasse wird automatisch gefunden (jede Klasse im Projekt, die von `CodeGenConfig` oder `DtoConfig<T>` erbt); ihre Methoden beschreiben nur, beim Build läuft nichts davon. So registrierte Facetten erreichen die OData-Facetten wie `[ProvideFacet]` (siehe [Facetten ohne Attribute](../web/odata.md#facetten-ohne-attribute)); konfiguriert werden sie in der Assembly der Entity. Die Referenz zur [Fluent-Konfiguration](https://fgilde.github.io/Nextended/de/projects/codegen#fluent-konfiguration-empfohlen) listet jede Methode: Views mit `ViewDefaults`, `Order`/`OrderLast`, Facetten und `DeleteStaleFiles` für generierte Dateien, die nicht mehr geschrieben werden. Typen und Attribute gehen typisiert hinein (`Attribute<T>(args)`, `BaseType<T>()`, `Interface<T>()`), Namen über `nameof`, damit ein Umbenennen in der IDE die Konfiguration erreicht. Jeder generierte Typ trägt `[GeneratedCode("Nextended.CodeGen", null)]` (Coverage und Analyzer überspringen ihn); `Defaults(d => d.GeneratedCodeAttribute(false))` lässt es weg.

## Mapping mit Extension-Methoden

Das ist der Standard. Brand bekommt Extension-Methoden in einer partiellen Klasse `MappingExtensions`:

```csharp
BrandDto dto = brand.ToDto();
Brand entity = dto.ToEntity();
dto.AssignTo(existingBrand);
```

Der Code besteht aus einfachen Zuweisungen und steht lesbar in `MyApp.Catalog/Generated/MappingExtensions.g.Brand.cs`. Braucht ein Feld mehr als eine Zuweisung, ergänzt `GenerateBeforeAndAfterAssignPartialsInMapping = true` partielle Hooks vor und nach den Zuweisungen.

## Mapping mit Mapperly

```csharp title="MyApp.Catalog/Domain/Product.cs"
[AutoGenerateDto(Namespace = "MyApp.Contracts.Catalog", MappingStrategy = DtoMappingStrategy.Mapperly)]
public sealed class Product : AuditedEntity, IMultiTenant { … }
```

Product bekommt stattdessen einen partiellen Mapperly-Mapper. Die Aufrufe sehen gleich aus (`product.ToDto()`); Mapperly schreibt die Implementierung beim Kompilieren und meldet Member, die es nicht abbilden kann.

```csharp title="MyApp.Catalog/Generated/ProductMapper.g.cs (erzeugt)"
[Mapper(RequiredMappingStrategy = RequiredMappingStrategy.Target)]
[UseStaticMapper(typeof(MyApp.Catalog.MappingExtensions))]
public static partial class ProductMapper
{
    public static partial ProductDto ToDto(this Product src);
    [MapperIgnoreTarget("TenantId")] /* … die übrigen ignorierten Spalten */
    public static partial Product ToEntity(this ProductDto src);
    public static partial void AssignTo(this Product src, [MappingTarget] ProductDto dest);
    [MapperIgnoreTarget("TenantId")] /* … */
    public static partial void AssignTo(this ProductDto src, [MappingTarget] Product dest);
}
```

Über `UseStaticMapper` nutzt die verschachtelte `Brand` das Mapping von Brand, beide Strategien lassen sich also beliebig mischen.

### Eine erzeugte Methode überschreiben

Der Mapper ist `partial`. Eine Methode mit demselben Namen im eigenen Teil der Klasse ersetzt die erzeugte, der erzeugte Teil lässt sie weg. Dasselbe gilt für das `[Mapper]`-Attribut, etwa um Einstellungen von Mapperly zu ändern.

```csharp title="MyApp.Catalog/ProductMapper.cs"
public static partial class ProductMapper
{
    [MapProperty(nameof(Product.Rate), nameof(ProductDto.Rate), Use = nameof(RoundRate))]
    public static partial ProductDto ToDto(this Product product);

    [UserMapping(Default = false)]
    private static decimal RoundRate(decimal rate) => Math.Round(rate, 2);
}
```

Hier geht der Preis des Produkts auf Cent gerundet hinaus; alles andere mappt weiterhin Mapperly. Methoden werden über den Namen zugeordnet, ein eigenes `AssignTo` übernimmt also beide Richtungen.

!!! note "Warum die Dateien auf der Platte liegen"
    Source-Generatoren sehen die Ausgabe anderer Generatoren nicht. Mapperly kann nur einen Mapper implementieren, der als echte Datei existiert; deshalb braucht die Mapperly-Strategie `OutputPath` und `MappingOutputPath`. Fehlen sie, enthält der erzeugte Mapper einen Kompilierfehler, der genau das sagt.

## Welche Variante

| | Extension-Methoden | Mapperly |
|---|---|---|
| Zusätzliches Paket | keins | `Riok.Mapperly` |
| Eigene Logik | partielle Hooks vor und nach den Zuweisungen | Mapperly-Attribute an der eigenen Deklaration, jede Methode ersetzbar |
| Prüfungen | keine, nicht abbildbare Member werden übersprungen | Mapperly meldet DTO-Member ohne Quelle |
| Geeignet für | einfache DTOs | DTOs mit Umbenennungen, Konvertierungen oder verschachtelten Objekten |

Enums sowie generische und abstrakte Entities mappen immer mit Extension-Methoden.

## Mit der CLI

`coworkee module add`, `coworkee entity add` und `coworkee entity import` richten all das mit `--codegen` ein (MCP-Werkzeuge `add_module`, `add_entity`, `import_entities`: `codegen: true`):

```bash
coworkee module add Crm --entity Customer -p Name:required:200 --codegen
coworkee entity add Crm Contact -p Email:email:required -p Customer:ref=Customer:required --codegen --mapping Manual
```

- Die Entity bekommt `[AutoGenerateDto(Namespace = "MyApp.Contracts.Crm")]`, mit `MappingStrategy = DtoMappingStrategy.Mapperly`, solange nicht `--mapping Manual` die Extension-Methoden verlangt. Das geschriebene DTO und Mapping entfallen; Handler, Endpunkte, Seite und API-Client nutzen das generierte `CustomerDto` und `ToDto()` genauso.
- Das Modulprojekt verweist auf `Coworkee.CodeGen` und für Mapperly auf `Riok.Mapperly`; `Directory.Packages.props` bekommt ihre Versionen.
- Neben dem Modulprojekt entsteht eine `codegen.json` wie oben, wenn es noch keine gibt; eine vorhandene wird nie geändert.
- Am Ende baut die CLI das Modul einmal. Dieser Build bricht am noch ungesehenen DTO ab, schreibt aber die Dateien, sodass der nächste `dotnet build` (oder `coworkee migrations add`) kompiliert. Beide `Generated`-Ordner gehören mit der Entity ins Repository.

Mapperly ist der Standard, weil der Generator es für diese Entities vollständig umsetzt (verschachtelte DTOs über `UseStaticMapper`, ausgelassene Spalten über `MapperIgnoreTarget`, Überschreiben über den Namen) und Mapperly ein DTO-Member ohne Quelle beim Kompilieren meldet. Ein generiertes DTO enthält das generierte DTO einer referenzierten Entity; die CLI nimmt Referenzen deshalb nur auf Entities desselben Moduls an, deren DTO ebenfalls generiert wird, und hält inverse Collections mit `[IgnoreOnGeneration]` aus dem DTO heraus, was auch eine Schleife Auftrag -> Kunde -> Aufträge verhindert.

## Ohne das Paket

Ohne `Coworkee.CodeGen` ändert sich nichts: DTOs und Mappings von Hand schreiben oder den Mapper der Wahl verwenden. Wird das Paket später entfernt, bleiben die erzeugten Dateien erhalten und sind ab dann normaler Quellcode.
