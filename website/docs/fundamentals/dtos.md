# DTOs and mapping

DTOs can be written by hand, and many are: requests, dashboards and other shapes that do not mirror an entity. For DTOs that do mirror one, the optional package `Coworkee.CodeGen` generates them from the entity, together with the mapping in both directions. It brings the [Nextended.CodeGen](https://fgilde.github.io/Nextended/projects/codegen) source generator; the mapping is either plain extension methods or a [Mapperly](https://mapperly.riok.app/) mapper, chosen per entity.

## Turn it on

Reference the package in the project that holds the entities, usually the module project:

```xml title="MyApp.Catalog/MyApp.Catalog.csproj"
<PackageReference Include="Coworkee.CodeGen" />
<!-- only for entities that map with Mapperly -->
<PackageReference Include="Riok.Mapperly" PrivateAssets="all" ExcludeAssets="runtime" />
```

and put a `codegen.json` next to the project file. The package picks it up by name; without it nothing is generated.

```json title="MyApp.Catalog/codegen.json"
{
  "DtoGeneration": {
    "Namespace": "MyApp.Catalog",
    "OutputPath": "../MyApp.Contracts/Catalog/Generated/",
    "MappingOutputPath": "./Generated/",
    "DeepProperties": true,
    "PropertiesToIgnore": [ "TenantId", "CreatedAt", "CreatedBy", "ModifiedAt", "ModifiedBy", "IsDeleted", "DeletedAt", "DeletedBy" ],
    "CreateFileHeaders": false,
    "CreateRegions": false,
    "DefaultMappingSettings": { "ToSourceMethodName": "ToEntity" }
  }
}
```

| Setting | Why |
|---|---|
| `OutputPath` | The DTOs are written into the contracts project, so the API, the Blazor client and the SDKs share them. The contracts project needs nothing for that. |
| `MappingOutputPath` | The mappings stay in the module project, the only one that knows entities and DTOs. |
| `Namespace` | Namespace of the mappings. The module's root namespace makes `brand.ToDto()` available in every handler without a `using`. |
| `DeepProperties` | Takes `Id` from `Entity` into the DTO. |
| `PropertiesToIgnore` | Columns no DTO should carry. An attribute can set its own list. |
| `CreateFileHeaders: false` | Keeps the time stamp out of the files, so a build only changes them when the entity changed. |
| `DefaultMappingSettings` | Method names; `ToDtoMethodName` defaults to `ToDto`. |

The generated files are ordinary source files in the repository: review them in the pull request like any other change. They are only rewritten when the build sees a changed entity, and a change shows up after the next build. Delete a file to have it generated again.

The files are written while the module compiles, after the contracts project is built, so code that uses a new DTO compiles from the next build on. To replace a hand-written DTO, mark the entity and build once while the hand-written DTO still exists, then delete it and its mapping.

## Mark the entities

```csharp title="MyApp.Catalog/Domain/Brand.cs"
[AutoGenerateDto(Namespace = "MyApp.Contracts.Catalog")]
public sealed class Brand : AuditedEntity, IMultiTenant
{
    public required string Name { get; set; }
    public string? Description { get; set; }
    public decimal Tax { get; set; }
    public Guid TenantId { get; set; }
}
```

```csharp title="MyApp.Contracts/Catalog/Generated/BrandDto.g.cs (generated)"
public partial class BrandDto : IBrandDto
{
    public required string Name { get; set; }
    public string? Description { get; set; }
    public decimal Tax { get; set; }
    public System.Guid Id { get; set; }
}
```

`required` members stay `required`, nullable members stay nullable, and the class is `partial`, so the contracts project can add to it. `[IgnoreOnGeneration]` on a property or `PropertiesToIgnore` on the attribute leaves members out; `[GenerationPropertySetting(PropertyName = ...)]` renames them. The [Nextended.CodeGen reference](https://fgilde.github.io/Nextended/projects/codegen) lists every option.

`Coworkee.CodeGen` brings Nextended.CodeGen 10.1.55. A second `[AutoGenerateDto]` on an entity generates one more DTO of it with its own mapping, a *view* (another shape for another client, a list row, an export): see [DTO views](https://fgilde.github.io/Nextended/projects/codegen#dto-views-several-dtos-of-one-entity). An entity with one attribute generates the same as before.

## Mapping with extension methods

This is the default. Brand gets extension methods in a partial `MappingExtensions` class:

```csharp
BrandDto dto = brand.ToDto();
Brand entity = dto.ToEntity();
dto.AssignTo(existingBrand);
```

The code is plain assignments you can read in `MyApp.Catalog/Generated/MappingExtensions.g.Brand.cs`. For a field that needs more than an assignment, `GenerateBeforeAndAfterAssignPartialsInMapping = true` adds partial hooks before and after the assignments.

## Mapping with Mapperly

```csharp title="MyApp.Catalog/Domain/Product.cs"
[AutoGenerateDto(Namespace = "MyApp.Contracts.Catalog", MappingStrategy = DtoMappingStrategy.Mapperly)]
public sealed class Product : AuditedEntity, IMultiTenant { … }
```

Product gets a partial Mapperly mapper instead. The call sites look the same (`product.ToDto()`); Mapperly writes the implementation at compile time and reports members it cannot map.

```csharp title="MyApp.Catalog/Generated/ProductMapper.g.cs (generated)"
[Mapper(RequiredMappingStrategy = RequiredMappingStrategy.Target)]
[UseStaticMapper(typeof(MyApp.Catalog.MappingExtensions))]
public static partial class ProductMapper
{
    public static partial ProductDto ToDto(this Product src);
    [MapperIgnoreTarget("TenantId")] /* … the other ignored columns */
    public static partial Product ToEntity(this ProductDto src);
    public static partial void AssignTo(this Product src, [MappingTarget] ProductDto dest);
    [MapperIgnoreTarget("TenantId")] /* … */
    public static partial void AssignTo(this ProductDto src, [MappingTarget] Product dest);
}
```

`UseStaticMapper` lets the nested `Brand` reuse Brand's own mapping, so both strategies mix freely.

### Overriding a generated method

The mapper is `partial`. Declare a method with the same name in your own part, and the generated part leaves it out. The same goes for the `[Mapper]` attribute, for example to change Mapperly's settings.

```csharp title="MyApp.Catalog/ProductMapper.cs"
public static partial class ProductMapper
{
    [MapProperty(nameof(Product.Rate), nameof(ProductDto.Rate), Use = nameof(RoundRate))]
    public static partial ProductDto ToDto(this Product product);

    [UserMapping(Default = false)]
    private static decimal RoundRate(decimal rate) => Math.Round(rate, 2);
}
```

Here the product's rate goes out rounded to cents; everything else is still mapped by Mapperly. Methods are matched by name, so declaring `AssignTo` takes over both directions.

!!! note "Why the files are on disk"
    Source generators cannot see each other's output. Mapperly can only implement a mapper that exists as a real file, which is why the Mapperly strategy needs `OutputPath` and `MappingOutputPath`. Without them the generated mapper contains a compile error that says so.

## Which one to take

| | Extension methods | Mapperly |
|---|---|---|
| Extra package | none | `Riok.Mapperly` |
| Custom logic | partial hooks before and after the assignments | Mapperly attributes on your own declaration, any method can be replaced |
| Checks | none, unmapped members are skipped | Mapperly reports DTO members without a source |
| Good for | simple DTOs | DTOs with renames, conversions or nested objects |

Enums, generic and abstract entities always use extension methods.

## With the CLI

`coworkee module add`, `coworkee entity add` and `coworkee entity import` set all of this up with `--codegen` (MCP tools `add_module`, `add_entity`, `import_entities`: `codegen: true`):

```bash
coworkee module add Crm --entity Customer -p Name:required:200 --codegen
coworkee entity add Crm Contact -p Email:email:required -p Customer:ref=Customer:required --codegen --mapping Manual
```

- The entity gets `[AutoGenerateDto(Namespace = "MyApp.Contracts.Crm")]`, with `MappingStrategy = DtoMappingStrategy.Mapperly` unless `--mapping Manual` asks for the extension methods. The written DTO and mapping are left out; handlers, endpoints, page and API client use the generated `CustomerDto` and `ToDto()` the same way.
- The module project references `Coworkee.CodeGen` and, for Mapperly, `Riok.Mapperly`; `Directory.Packages.props` gets their versions.
- A `codegen.json` like the one above is created next to the module project when it has none; an existing one is never changed.
- At the end the CLI builds the module once. That build stops at the DTO it has not seen yet, but writes the files, so the next `dotnet build` (or `coworkee migrations add`) compiles. Commit both `Generated` folders with the entity.

Mapperly is the default because the generator implements it fully for these entities (nested DTOs through `UseStaticMapper`, ignored columns through `MapperIgnoreTarget`, overrides by name) and Mapperly reports a DTO member without a source at compile time. A generated DTO contains the generated DTO of a referenced entity; the CLI therefore accepts references only to entities of the same module whose DTO is generated too, and keeps inverse collections out of the DTO with `[IgnoreOnGeneration]`, which also stops an order -> customer -> orders loop.

## Leaving it out

Without `Coworkee.CodeGen`, nothing changes: write DTOs and mappings by hand, or use the mapper you prefer. Removing the package later keeps the generated files; they are plain source from then on.
