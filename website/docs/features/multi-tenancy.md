# A multi-tenant SaaS foundation for .NET

A SaaS product serves many customers from one installation. Each customer expects to see only their own data, to configure the app their way and to get the features of the plan they pay for. Getting tenant isolation wrong once is enough to lose a customer, and bolting it onto an existing single-tenant app means touching every query.

In Coworkee the tenant is part of the foundation. Every request knows its user and tenant, EF Core filters tenant data on its own, settings resolve from the installation down to the single user, and the features module turns parts of the app on and off per tenant through editions. The same code runs as a single-company app or as a platform for hundreds of organisations.

## Tenants and organisations

A tenant is an organisation with a name, an identifier and an active flag. Users, roles, groups, permission grants and the data of your modules belong to one tenant. One organisation is the system organisation: it hosts the installation-wide administration. Its administrators open *Administration > Tenants* to create organisations (optionally with a first administrator), activate and deactivate them and assign an edition. A deactivated organisation also stops the API keys of its users.

Some permissions only make sense for the host, such as `Features.Tenants`, `Features.Editions` and `Identity.Clients.Manage`. Every administrator holds them, but only administrators of the system organisation can use them.

## Tenant filters in EF Core

An entity opts in with one marker interface:

```csharp
public sealed class Order : AuditedAggregateRoot, IMultiTenant
{
    public Guid TenantId { get; set; }
    public required string Number { get; set; }
}
```

`CoworkeeDbContext` then adds a named query filter on the current tenant, so `db.Set<Order>()` returns only the rows of the caller's organisation. On insert, `TenantId` is set from the current user; saving a row into a foreign tenant throws. Code generated by `coworkee entity add` uses `IMultiTenant` by default, and its unique indexes are unique per tenant.

`ICurrentUser` carries user id, tenant id and permissions of the request. Background jobs and the outbox restore the user and tenant that started them, and code that has to act for another tenant, such as a seed, opens a scope:

```csharp
using (CurrentUserScope.Begin(new ImpersonatedUser(adminId, tenantId)))
{
    // queries and inserts run as this user and tenant
}
```

Cached queries are shared per tenant by default (`CacheScope.Tenant`), so one customer's dashboard never answers another's.

## Settings per installation, tenant and user

Settings are single values with a type and one or more scopes: `Global`, `Tenant` and `User`. The most specific value wins, so an organisation can override the installation's default language and a user can override both.

```csharp
context.Group("Billing", "Billing")
    .Add("Billing.Currency", "Currency", SettingType.Choice, [SettingScope.Tenant], "EUR", choices: ["EUR", "USD", "CHF"])
    .Add("Billing.ApiKey", "API key", SettingType.Secret, [SettingScope.Global]);
```

A setting appears on the admin page as soon as its `ISettingDefinitionContributor` is registered: *System* for global values, *Organisation* for tenant values, *My settings* for the user. No form code per setting. Secrets are encrypted with ASP.NET Core data protection and never sent to the client. Code reads values with `ISettingProvider.GetAsync<T>`.

## Typed app configuration with Lock and Protect

For larger blocks of configuration the app describes its settings as a C# class. Values come from appsettings and the environment; what administrators change in the app is stored in the database and lies on top for every service, read through `IOptionsMonitor<T>`. Rules decide what the browser may touch:

```csharp
context.Services.AddCoworkeeSettings<MyAppSettings>(context.Configuration, rules => rules
    .Lock(s => s.Billing.Currency)          // shown disabled, never changed
    .Protect(s => s.Billing.WebhookUrl)     // editable once its lock button is pressed
    .Hide(s => s.Billing.WebhookSecret));   // never leaves the server
```

Typed settings apply to the whole installation and are edited from the system organisation; values per tenant and per user are settings.

## Features and editions

`Coworkee.Features` switches parts of the app on and off per tenant. Modules define features of type `Bool`, `Int` or `String`, editions bundle feature values, and every tenant gets an edition plus its own overrides. A tenant's value comes from its override, then its edition, then the default.

```csharp
[RequiresFeature("Reports.Enabled")]
public sealed record CreateReport(string Name) : ICommand<Result<Guid>>;
```

The dispatcher answers `403` with the code `feature.disabled` while the feature is off; minimal APIs use `.RequireFeature(...)`, and `IFeatureChecker` answers in code. In Blazor, `FeatureGate` and navigation items with a `Feature` hide what the edition does not include, and a change reaches open clients over realtime. Administrators maintain editions under *Administration > Editions* and limits such as reports per month per tenant without a deployment.
